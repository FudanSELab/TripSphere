## F1\-F5 系统改造总目标与逐服务落地方案

本节把前面 F1\-F5 的“逐服务待完成内容”进一步收敛成一次系统改造方案。目标不是继续堆叠服务，而是先形成一条可验证的业务主链路，再围绕这条主链路准备故障数据。所有服务都必须回答三个问题：

1. 是否属于最终系统的真实业务闭环；

2. 如果保留，具体要补哪些实现和接入；

3. 改造完成后，如何证明它已经可以作为稳定业务基线。

### 1\. 最终系统范围

最终系统聚焦六条用户可感知的业务：

| 业务闭环   | 最终目标                                                     |
| ---------- | ------------------------------------------------------------ |
| 用户与身份 | 用户注册、登录、JWT 会话、服务间身份传递和所有权校验统一     |
| 内容浏览   | 景点、酒店、房型、商品和基础地理信息可以被前端和 planner 稳定读取 |
| AI 行程    | 用户提交目的地和偏好后生成可执行行程，保存到 itinerary service，并可通过 co\-agent 修改 |
| 评论业务   | 用户可查看、创建、更新、删除自己的评论；酒店/景点评论可被 review\-summary 索引 |
| 评论问答   | chat agent 通过 `trip-review-summary` 的 MCP 工具查询指定酒店或景点的评论总结，并返回证据和索引状态 |
| 订单业务   | 用户从商品/SKU 形成草稿，确认后创建订单，查询订单，取消订单，模拟支付并确认库存 |

改造完成后，核心链路应为：

```Plaintext
frontend
  -> auth/user
  -> attraction/hotel/product
  -> itinerary-planner -> itinerary-service
  -> review-service -> review-summary MCP -> chat-service
  -> chat-service -> order-assistant -> product/order-service -> inventory-service
```

`trip-review-summary-worker` 是 review\-summary 的异步运行角色，不是独立业务领域；它和 API/MCP 使用同一个项目、同一套索引版本和任务状态。

### 2\. 服务取舍决策

| 服务 / 组件                             | 最终处理               | 决策理由                                                     |
| --------------------------------------- | ---------------------- | ------------------------------------------------------------ |
| `trip-next-frontend`                    | 保留并补齐             | 是唯一用户入口，当前缺评论和完整订单支付入口                 |
| `trip-user-service`                     | 保留并改造             | 是身份签发方，但身份尚未贯穿订单和评论服务                   |
| `trip-attraction-service`               | 保留                   | 前端和 planner 都已经使用，是景点主数据源                    |
| `trip-hotel-service`                    | 保留                   | 前端和 planner 都已经使用，是酒店/房型主数据源               |
| `trip-product-service`                  | 保留并补齐             | 订单和房型展示依赖 SKU/SPU，需要成为稳定商品事实源           |
| `trip-inventory-service`                | 保留并改造             | 订单服务真实依赖库存锁、确认和释放                           |
| `trip-order-service`                    | 保留并改造             | 订单状态、库存协同和过期调度的核心服务                       |
| `trip-itinerary-service`                | 保留并改造             | 行程持久化和用户访问控制已经存在                             |
| `trip-itinerary-planner`                | 保留并改造             | AI 规划和 co\-agent 编辑的核心服务                           |
| `trip-chat-service`                     | 保留并改造             | 主聊天入口，负责记忆、工具和 agent 委派                      |
| `trip-order-assistant`                  | 保留并改造             | 订单领域 Agent，由 chat 通过 A2A 委派                        |
| `trip-review-service`                   | 保留并接入             | 评论主数据已经存在，但当前没有前端和 summary 调用方          |
| `trip-review-summary`                   | 保留并改造为 MCP 服务  | 作为 chat agent 的评论问答工具，不再依赖人工 A2A 才能使用，删除A2A部分 |
| `trip-review-summary-worker`            | 保留为异步 worker 角色 | 负责评论索引构建、重建和状态更新，使用同一镜像和代码库       |
| `trip-poi-service`                      | 删除出最终运行系统     | 当前没有业务调用方，且景点服务已承担 planner 的候选检索      |
| `trip-file-service`                     | 删除出最终运行系统     | 当前没有业务调用方；评论图片/笔记附件不属于本次主闭环        |
| `trip-note-service`                     | 删除出最终运行系统     | 只有 metadata 接口，没有 Note 领域实现；前端页面也是占位     |
| `trip-note-creator`                     | 删除                   | 只有脚手架，没有入口和业务逻辑                               |
| RocketMQ `rmq-*`                        | 删除                   | review\-service 当前没有 producer/consumer；评论索引改用显式任务提交和 Redis/Celery |
| `nacos`                                 | 保留并统一             | 同时承担服务发现和 AgentCard/MCP 相关注册配置                |
| `higress`                               | 保留并固化配置         | 所有 LLM、structured output 和 embedding 统一经过该网关      |
| MongoDB/PostgreSQL/Redis                | 保留并分工             | 分别承载文档、事务数据、缓存/幂等/Celery 状态                |
| Qdrant/Neo4j                            | 保留                   | review\-summary 的向量、图谱和索引中间产物需要它们           |
| OTel Collector/Tempo/Prometheus/Grafana | 保留                   | F1\-F5 样本需要能够定位延迟、错误、重试和跨服务调用          |

删除服务时同步删除其 Docker Compose、Taskfile include、构建任务、无调用方的客户端、相关初始化脚本和专属 proto。不能只从 Compose 删除而让仓库继续把这些服务当成可构建目标。

### 3\. 逐服务改造目标

#### `trip-next-frontend`

**需要完成的系统实现**

- 保留当前 Server Actions \+ 静态 gRPC \+ Copilot Runtime 架构，统一从 session/JWT 产生 `authorization`、`x-user-id`、`x-user-roles` metadata。

- 新增 Review gRPC client 和 server actions，接入酒店、景点详情页的评论列表、评分、评论数、当前用户评论、创建、更新、删除。

- 将酒店详情页的“点评”占位内容替换为真实 ReviewService 数据；酒店卡片和景点详情页不再显示固定的 `0` 或空文本。

- 在酒店/景点详情页的 chat AG\-UI context 中传递不可由用户文本覆盖的 `target_id`、`target_type`、`entity_name`。

- 增加完整订单入口：从房型/SKU 选择进入草稿或直接下单，展示 pending payment 订单，调用 `ConfirmPayment`，展示 paid/cancelled 状态。

- 订单取消、支付、评论更新和行程替换都必须使用认证 metadata，不能只传业务对象中的 user id。

- co\-agent 保存增加最后一次变更 flush、失败重试、版本冲突提示和 stream 重连后的去重。

- 删除未使用的 `POI_SERVICE_ADDR`、File/Note 入口和没有可见业务页面的直接 `order_assistant` Copilot agent 配置；订单 Agent 只通过 chat 委派。

**最终目标**

用户可以在一个登录会话中完成“浏览酒店/景点 \-\> 查看评论 \-\> 询问评论总结 \-\> 生成行程 \-\> 修改并保存 \-\> 选择商品下单 \-\> 支付/取消”的完整流程。前端所有写操作都能被后端按登录用户校验。

#### `trip-user-service`

**需要完成的系统实现**

- 保留注册、登录和 JWT 签发；统一 JWT 的 `sub`、roles、issuer、过期时间和 key 配置。

- 明确 user\-service 是身份签发方，不作为每个业务请求的同步鉴权依赖；业务服务通过签名 JWT/统一 metadata 自己完成认证。

- 为 Java、Go、Python 服务定义统一身份契约：`authorization` 原始 bearer token、`x-user-id` 由可信入口提取、`x-user-roles` 仅作授权辅助，业务服务不得信任请求体中的 user id 覆盖认证身份。

- 保留 `GetCurrentUser`，由 frontend session 校验或账户页调用，避免接口成为无调用的孤立能力。

- 提供成对的 RSA key 配置和启动校验；frontend public key 与 user\-service private key 不一致时必须在启动/健康检查阶段明确失败。

**最终目标**

所有需要用户归属的服务都能从同一套认证上下文得到用户身份。订单、评论、行程和草稿不会因为请求体伪造 user id 而越权。

#### `trip-attraction-service`

**需要完成的系统实现**

- 继续作为景点主数据服务，保留前端列表/详情/附近查询和 planner `GetAttractionsNearby`。

- 在 Nacos 注册时显式写入 `gRPC_port`、协议、健康状态和容器可达 host。

- 为 planner 提供稳定的候选排序、limit、标签和城市过滤语义；空结果必须能区分“没有景点”和“服务失败”。

- 补 `BatchGetAttractions` 的真实调用或将其从公开 contract/故障候选中移除；不能保留没有任何消费者的扩展接口。

- 初始化脚本准备城市为上海。

**最终目标**

前端和 planner 对同一景点事实使用同一数据源；planner 在候选少于请求数量时仍能返回实际候选，不会因为固定采样逻辑丢失全部结果。

#### `trip-hotel-service`

**需要完成的系统实现**

- 继续作为酒店、房型和酒店地理信息主数据服务。

- 显式注册 `gRPC_port`，统一 Nacos 服务名和容器地址。

- 为酒店附近查询补充“无酒店”和“依赖失败”两种可区分返回状态，planner 不得把二者都转换成正常空酒店。

- 与 product\-service 明确房型资源 id、SPU/SKU 的映射；同一房型在详情展示、订单草稿和订单校验中必须使用相同 SKU。

- 接入真实评论只通过 review\-service，不在 hotel\-service 内复制评论数据。

- 初始化脚本准备酒店、房型、价格关联和可售 SKU。

**最终目标**

用户能从酒店详情直接进入房型、评论和订单；planner 生成的住宿信息可以被商品服务识别并继续下单。

#### `trip-product-service`

**需要完成的系统实现**

- 继续作为 SPU/SKU 唯一事实源，保留前端房型价格展示、order\-service 批量校验和 order\-assistant 查询。

- 显式注册 `gRPC_port`；统一商品状态、资源类型、价格和日期可售字段。

- 为 `CreateSpu`、`BatchCreateSpus`、`UpdateSpu` 决定最终用途：若没有运营后台调用，则从最终业务 contract 和故障注入清单中删除；初始化数据统一由 `infra/initializer` 导入。

- `GetSkuById` 返回资源类型、所属酒店/景点、价格、上下架状态和可售区间，order\-assistant 添加草稿时必须校验这些字段。

- 补不存在 SKU、下架 SKU、资源类型不匹配和日期不可售的确定性业务错误。

**最终目标**

任何订单金额、资源类型和可售判断都基于 product\-service 的稳定数据，agent 不能仅凭自然语言或前端展示值创建订单。

#### `trip-inventory-service`

**需要完成的系统实现**

- 保留 Postgres 日库存、库存锁、确认、释放和过期扫描。

- 显式注册 `gRPC_port`；统一 `LockInventory`、`ConfirmLock`、`ReleaseLock` 的幂等结果和错误码。

- 以数据库状态为权威，Redis 仅作为缓存、互斥和过期索引；缓存失败不能改变库存业务结果。

- 过期 scheduler 处理失败时保留 expiry 记录并重试，不能先删除任务再记录日志。

- 增加锁释放失败的补偿记录和可查询状态，供 order\-service 判断订单是否允许进入最终取消状态。

- 补库存不足、重复锁、重复确认、重复释放、锁过期和服务重启测试。

**最终目标**

订单服务能可靠地完成“锁库存 \-\> 支付确认”或“锁库存 \-\> 取消释放”，不会出现订单状态已完成但库存仍被占用，也不会因 Redis 故障丢失数据库事实。

#### `trip-order-service`

**需要完成的系统实现**

- 从认证 metadata 得到 user id，忽略或校验请求体中的 `user_id`；Get、GetByNo、List、Cancel、Confirm 全部做订单归属校验。

- 保留 `request_id` 幂等，并将幂等记录从“Redis 失败即放行”改为明确的拒绝、数据库兜底或可观测降级。

- 将订单状态机明确为 `PENDING_PAYMENT -> PAID -> COMPLETED`，或明确本系统只做到 `PAID`；若保留 `COMPLETED`，必须实现完成入口和触发条件。

- 明确 `ConfirmPayment` 是模拟支付

- 取消库存释放失败时返回待补偿状态或不完成取消，不得返回成功后只写日志。

- 订单过期 scheduler 失败时保留任务；订单号、request id、库存 lock id 和补偿记录必须可追踪。

- 为 frontend 和 order\-assistant 提供一致的查询、取消、支付响应结构，补端到端订单测试。

**最终目标**

一个订单只能属于一个用户，创建、取消、支付、过期和库存状态可追踪、可重试、可恢复；agent 重试不会重复创建或错误取消订单。

#### `trip-itinerary-service`

**需要完成的系统实现**

- 保留 gRPC CRUD 和 Mongo 持久化，继续作为行程唯一持久化事实源。

- 所有读取、列表、替换、删除和 activity 操作继续使用认证上下文进行所有权校验。

- 为 ReplaceItinerary 增加 `version` 或 `updated_at` 条件，前端 debounce 保存不能静默覆盖较新的版本。

- 对行程日期、day number、activity id、坐标、时间区间和关联 hotel/attraction id 做服务端结构校验，不信任 agent 生成的任意 JSON。

- 明确 planner 非流式创建与 frontend co\-agent 替换的保存顺序，避免“页面显示成功但数据库没有结果”。

**最终目标**

行程在服务重启、前端刷新、agent 多轮修改和并发保存后仍然是可恢复、可验证、属于正确用户的结构化数据。

#### `trip-itinerary-planner`

**需要完成的系统实现**

- 保留非流式规划接口作为唯一“生成并持久化”的正式业务入口；流式接口只用于进度展示，完成后必须引用同一个 planning job/result。

- 修复候选不足时 `random.sample(..., 15)` 的固定采样问题，按 `min(requested, available)` 处理。

- 对日期范围、天数、活动数量、时间重叠、坐标、城市归属、景点 id 和酒店 id 做最终结构化校验。

- 地理编码、景点、酒店、LLM 失败必须返回结构化 `dependency_unavailable`、`no_data`、`model_failed` 等状态；禁止用固定上海坐标伪装任意目的地。

- 所有 Nacos gRPC 依赖统一使用 metadata；增加 timeout、有限重试和不可重试错误分类。

- 行程 Markdown 只能描述结构化 itinerary 中真实存在的活动；生成失败使用模板但要标记降级原因。

- 将 MemorySaver 替换为共享持久化 checkpoint，或明确 planner chat 只在单实例短会话中使用；frontend co\-agent 保存使用版本条件。

- SSE 增加 job id、event id、最后状态、重连和结果查询接口，避免中断后重新生成产生重复行程。

**最终目标**

planner 输出的每个活动都能在目的地、日期和时间上执行，且生成结果一定能对应一个持久化 itinerary id；故障时用户知道是无数据、依赖失败还是模型失败。

#### `trip-chat-service`

**需要完成的系统实现**

- 保留 Mongo session、Mem0/Qdrant memory、AG\-UI/ADK 和默认聊天入口。

- 将远程 agent 名单和 endpoint 配置化；默认发现 `order_assistant`，通过 MCP 发现/连接 `trip-review-summary`，注册到Nacos上，不再依赖 review\-summary A2A 作为主路径。

- 增加 review MCP toolset，至少提供 `query_review_summary`、`get_review_index_status`；构建索引属于后台/受控工具，不应让普通聊天任意触发昂贵重建。

- 对酒店/景点详情页上下文校验 `target_id`、`target_type` 和来源，用户文本不能覆盖系统实体上下文。

- 工具 retry 按只读和副作用分类；查询可以有限重试，下单、取消、支付必须依赖幂等键或禁止自动重试。

- 模型、MCP、A2A 和 memory 错误使用结构化状态，最终回复不得把技术失败说成“没有评论”“订单不存在”等业务事实。

- 健康检查真实探测 Mongo、Qdrant、Higress、Nacos 和必要的 MCP endpoint。

**最终目标**

chat 能正确完成普通旅游问答、基于当前实体的评论问答和订单委派；记忆按用户隔离，远程能力缺失可见，副作用工具不会因模型重试重复执行。

#### `trip-order-assistant`

**需要完成的系统实现**

- 保留为订单领域 Agent，只由 chat 通过 A2A 委派；若未来没有独立订单页面，删除 frontend 对它的直接 Copilot runtime 注册。

- 将 AgentCard 的 URL、技能、输入输出模式配置化，并与真实工具能力一致；输出统一为 A2A text response 或明确的结构化结果协议。

- 将 `ORDER_DRAFTS` 迁移到 Redis，并以 `draft_id + owner_user_id` 校验每次读取、修改、删除和提交。

- 草稿添加商品前校验 SKU 资源类型、日期、end date、quantity、库存可售和价格快照；补联系人来源。

- 取消必须由工具层保存 confirmation token/过期时间，`cancel_order` 没有有效确认状态时不可执行。

- 提交订单使用稳定 idempotency key，成功后删除或标记草稿；补 `confirm_payment` 和订单状态查询工具。

- 所有 gRPC 调用转发 authorization/user metadata，不能只把 user id 放进 CreateOrder request。

**最终目标**

Agent 能把用户意图转换为可检查的订单草稿，并在确认后只创建一次属于当前用户的订单；任何错误都能说明发生在商品、库存、订单还是支付阶段。

#### `trip-review-service`

**需要完成的系统实现**

- 增加 frontend Review gRPC client 的真实调用入口；酒店和景点详情页支持列表、当前用户评论、创建、编辑、删除。

- Create/Update/Delete 的用户身份从 `x-user-id` metadata 得到，不能信任 review message 的 user id；Update/Delete 必须按 `review_id + owner_user_id` 查询/删除。

- 保留 entity type `hotel` 和 `attraction`，增加评分聚合/评论总数接口或稳定的 stats response，供详情页和 summary 使用。

- 为评论内容、图片 URL、维度、评分、时间字段补确定性校验；保留 `updated_at` 作为索引版本输入。

- 选择不使用 RocketMQ；评论写入成功后提交 review index refresh job，至少支持异步触发和定时 reconciliation，不能只依赖人工调用。

- 为 review\-summary 提供稳定 gRPC 地址和分页读取能力，确保它能拉取同一实体的完整评论快照。

**最终目标**

评论成为可被用户真实读写的主数据，作者权限可靠，评论变更能够最终反映到 review\-summary 索引，不会出现前端有评论但 Agent 永远查不到的断链。

#### `trip-review-summary`

**需要完成的系统实现**

- 保留同一个项目，新增 Streamable HTTP MCP endpoint，例如 `/mcp`；不新增独立 review MCP 服务。

- MCP 工具最小集合：

  - `query_review_summary(target_id, target_type, question)`：返回答案、引用 review/text unit、索引版本、更新时间和数据不足状态；

  - `get_review_index_status(target_id, target_type)`：返回 `never_built/building/ready/stale/failed/empty`；

  - `request_review_index(target_id, target_type, force)`：只允许受控调用，提交异步索引任务并返回 task id。

- `trip-review-summary` 增加 ReviewService gRPC client，通过 Nacos 或稳定 env 地址分页调用 `ListReviewsByEntity`，支持酒店和景点。

- 首次索引流程改为 `review-service -> review snapshot -> text units -> Qdrant -> graph extraction -> Neo4j -> index metadata`；每个阶段写入 task state、input review version、output index version 和失败原因。

- Qdrant payload 必须包含 `review_id`、`target_id`、`target_type`、`rating`、`dimensions`、`created_at`、`updated_at`、`source`；Neo4j 节点和关系也必须带目标过滤字段。

- 删除A2A executor、LocalSearch、vector store 的 `target_type` 贯穿；不再默认 attraction，也不再拒绝 hotel。

- 使用 Mongo 持久化 index metadata 和 task state；Redis/Celery 只负责排队和执行，不把进程内存作为业务状态。

- 实现按目标删除/重建、过期判断、空评论状态、无索引状态和数据不足回答；回答不能把技术失败伪装成“没有差评”。

- 静态 summary 若没有前端或 Agent 调用方，从最终业务中删除 `/summaries` 和对应未实现 task；主业务只保留实时 query summary。

- review\-summary 不再作为 chat 默认 A2A remote agent；完成 MCP 迁移后删除 production AgentCard、A2A `InMemoryTaskStore` 和对应主链路配置。数据集不需 A2A 故障样本。

**最终目标**

用户在酒店/景点详情页或主聊天中询问评论时，chat 能通过 MCP 定位正确实体，返回基于真实评论的总结、证据和索引状态；评论新增/更新后，索引最终一致且可观察。

#### `trip-review-summary-worker`

**需要完成的系统实现**

- 继续使用 `trip-review-summary` 镜像，以 worker command 运行，不新增领域服务。

- Celery 统一发现实际保留的 index/sync tasks；删除静态 summary 和 graph embedding 的未实现任务，或实现后再重新加入。

- 每个 task 使用目标级幂等键，重复执行不会重复污染 Qdrant/Neo4j；任务状态持久化到 Mongo，结果和中间文件使用Mongo。

- 增加任务重试阶段、最大重试次数、失败原因和人工重建入口；Qdrant、Neo4j、Higress 依赖失败必须能区分可重试和不可重试。

- worker 启动健康检查 Redis、Qdrant、Neo4j 和 Higress，compose 中显式声明依赖。

**最终目标**

review\-summary 的索引构建不会阻塞 chat 请求，任务可以重试、重启后继续查询状态，且一次评论快照对应一个可追踪的索引版本。

#### `infra/initializer`

**需要完成的系统实现**

- 保留为一次性初始化工具，不作为常驻服务。

- 保留 hotels、room types、attractions、SPUs、inventories 初始化；POI 初始化不用落库，但是其他数据需要POI数据作为支撑。

- 增加 users、reviews、review index fixtures，至少覆盖两个用户、酒店评论、景点评论、空评论、恶意文本和更新后的评论。

- 初始化数据必须与最终 compose 的数据库账号、数据库名、服务端口和容器网络一致；命令支持容器内和宿主机两种连接方式。

- 初始化完成后输出每类数据的数量和关键 id，供端到端冒烟脚本使用。

**最终目标**

任何开发或故障样本环境都能用同一套命令得到确定性基础数据，不再因为空库、错误 SKU 或缺少评论而把基础设施问题误认为业务故障。

#### `trip-poi-service`

**最终目标**

#### `trip-file-service`

#### `trip-next-frontend` 之外的部署与基础设施

**需要完成的系统实现**

- OTel trace 中统一 service name、user/session/request/task/index version，Prometheus/Grafana 能观察 planner、order、review MCP 和 worker。

**最终目标**

### 5\. 改造完成验收顺序

1. **基础环境验收**：canonical compose 启动，所有保留服务健康，Nacos 注册地址可达，Higress chat/embedding 路由成功。

2. **基础数据验收**：initializer 导入用户、景点、酒店、房型、SKU、库存和评论；输出固定数量与 id。

3. **身份验收**：用户 A/B 分别登录，订单、评论、行程、草稿和 Mem0 不能跨用户读取或修改。

4. **内容验收**：前端景点/酒店列表、详情、房型和真实评论展示成功。

5. **行程验收**：表单生成行程并持久化；co\-agent 修改、刷新、重启后仍能恢复；错误能区分无数据和依赖失败。

6. **评论 MCP 验收**：评论变更触发索引任务；`query_review_summary` 能正确区分 hotel/attraction，返回答案、引用、索引版本和数据不足状态。

7. **订单验收**：商品 \-\> 草稿 \-\> 用户确认 \-\> 创建订单 \-\> 锁库存 \-\> 模拟支付 \-\> paid \-\> 取消/过期释放库存全链路成功，重复请求只产生一个订单。

8. **观测验收**：每条请求都能按 request id、user id、task id、index version 在日志、trace 和指标中定位。

9. **故障基线验收**：只有通过上述业务验收的服务和入口，才重新标记为 F1\-F5 “可以准备注入”；被删除或实验 profile 的入口从正式样本清单移除。

### 6\. 改造后的最终判定标准

系统改造完成不等于所有服务都能启动，而是满足以下条件：

- 每个保留服务都有真实调用方、明确所有权和可验证的成功路径；

- 每个异步任务都有持久化状态、幂等键、失败原因和重试边界；

- 每个 Agent 工具都能区分只读操作和副作用操作；

- 每个外部数据源都能区分空数据、过期数据和依赖故障；

- review\-summary 已成为 chat 可调用的 MCP 工具，而不是孤立的人工 A2A 示例；

- 未接入的服务和入口已经删除，不会继续污染 F1\-F5 注入点；

- F1\-F5 故障只在业务正确性先验成立的前提下执行。
