# TripSphere 基础业务闭环改造清单

**文档状态：** Phase 1 已完成，本文档为后续基础功能实施范围
**改造目标：** 完成六条用户可验证的业务闭环，接通单实例运行所需的基础设施与可观测性，并删除没有业务调用方的服务。
**基本原则：** 基础功能、依赖、部署和观测必须正确可用；不要求高可用集群和复杂故障恢复。

## 1. 本轮范围

本轮必须完成以下六条闭环：

| 闭环 | 完成标准 |
| --- | --- |
| 用户与身份 | 注册、登录、JWT 会话可用；业务写操作使用认证身份；用户不能访问其他用户的订单、评论和行程 |
| 内容浏览 | 前端可以读取景点、酒店、房型、商品和 SKU；规划器使用同一套景点/酒店数据 |
| AI 行程 | 用户提交目的地和偏好后生成并保存行程；前端可以读取、编辑和重新保存 |
| 评论业务 | 用户可以查看酒店/景点评论，创建、修改和删除自己的评论；详情页显示评分和评论数 |
| 评论问答 | 聊天可以根据当前酒店/景点查询真实评论并返回总结；没有评论、没有索引和服务失败要能区分 |
| 订单业务 | SKU 选择、订单创建、订单查询、取消和模拟支付可用；库存锁定、确认和释放结果正确 |

### 不作为本轮完成条件的内容

- 不新增真实支付渠道，`ConfirmPayment` 成功后订单保持 `PAID`。
- 不要求把所有服务改造成高可用集群，不要求副本、自动故障转移、跨实例一致性、共享 checkpoint、完整补偿系统或复杂重试框架。
- 不要求完成 F1-F5 故障注入；但 Loki、OTel、Tempo、Prometheus、Grafana、Higress、Nacos 和 Compose 基础接入属于本轮必做。
- 不因为“可能以后会用到”而新增服务、消息系统、数据库或管理后台。
- 不强制把已有订单 A2A 改成其他协议；评论问答使用能最快形成真实业务闭环的现有调用入口。

### 删除

以下项目没有六条闭环的业务调用方，应在调用引用清理后删除：

| 项目 | 删除内容 |
| --- | --- |
| `trip-poi-service` | 服务目录、Compose 服务、Taskfile include/build 入口、独立 POI gRPC service 生成目标和前端 POI client/config |
| `trip-file-service` | 服务目录、Compose 服务、Taskfile include/build 入口、File gRPC 生成目标 |
| `trip-note-service` | 服务目录、Compose 服务、Taskfile include/build 入口和 Note 生成目标 |
| `trip-note-creator` | 目录、构建入口和文档引用 |
| RocketMQ | `rmq-*` Compose 服务、ReviewService 的无效 `ROCKETMQ_ENDPOINT` 和相关配置 |

删除 MinIO 前必须先处理 `trip-review-summary` 当前用于索引中间文件的 S3/MinIO 依赖。若本轮不改索引中间文件实现，则 MinIO 暂时保留，不能把它误判成无调用方服务；它列为下一次清理项，而不是本轮强删项。

删除服务时必须同步检查：

- `docker-compose.yaml`、`deploy/docker-compose/docker-compose.yaml`
- 根 `Taskfile.yaml`、各服务 Taskfile 和构建脚本
- `contracts/protobuf` 及各服务生成代码入口
- 前端环境变量、gRPC client、Server Action 和导航
- Nacos/Higress 配置、初始化脚本、README 和测试客户端

## 4. 实施阶段

### Phase 2：身份、内容和基础数据

目标：让登录后的用户能够稳定读取内容并携带认证上下文。

- 保留 Phase 1 的服务发现实现，验证 planner 能发现 attraction/hotel，order-assistant 能发现 product/order。
- 沿用现有 frontend session、请求头和 gRPC metadata 传递方式；本轮只验证现有链路可用，不新增 metadata 统一生成或认证架构改造。
- user-service 继续负责签发 JWT；order、review、itinerary 沿用当前身份参数和接口行为，只修复会阻断业务闭环的调用问题。
- 处理 frontend 的 `POI_SERVICE_ADDR`、`getPoiService` 和无调用入口。
- 确认 attraction、hotel、product 的基础数据、SKU 和房型映射；初始化脚本输出可用于验收的固定 id。
- 只修复会阻断六条闭环的空数据、错误端口、错误资源类型和不明确错误返回。

完成标准：用户可以登录，前端可以读取景点/酒店/房型/SKU，planner 和 order-assistant 可以通过服务发现读取同一份事实数据。

### Phase 3：AI 行程闭环

目标：完成“生成、保存、读取、编辑、再次保存”。

- 以现有非流式规划接口作为正式生成入口，确保生成完成前保存到 itinerary-service。
- 修复候选数量少于请求数量时的固定采样错误。
- 校验目的地、日期、活动、景点/酒店 id 和基础坐标；不能用固定上海坐标冒充其他目的地。
- 继续使用现有 `ReplaceItinerary` 保存编辑结果，确保当前登录会话下的读取和替换流程可用。
- 不把共享 checkpoint、SSE job/result、并发版本控制列为本轮前置；只有现有保存行为确实丢数据时才补最小修复。

完成标准：用户可以生成行程、刷新后读取、编辑后保存。

### Phase 4：评论与评论问答闭环

目标：让评论成为真实主数据，并让聊天基于真实评论回答。

- frontend 接入 review-service 的列表、当前用户评论、创建、更新、删除和评分/数量展示。
- review-service 沿用当前作者身份和 CRUD 参数传递方式，只修复会阻断评论闭环的接口问题。
- review-summary 通过 review-service 的 `ListReviewsByEntity` 获取酒店和景点评论，不能继续依赖默认 attraction 或预置 text unit。
- 保留现有 review-summary 的索引任务和 A2A 调用方式作为本轮最小集成路径；只删除未实现的静态 summary 入口，不强制做 MCP 协议迁移。
- 评论问答必须接收并校验 `target_id`、`target_type`；空评论、尚未建立索引和依赖失败返回不同状态。
- chat 接入 review-summary，详情页上下文提供不可由用户文本覆盖的实体 id/type。
- 索引中间文件继续使用当前已配置的存储方式，避免为了删除 MinIO 扩大本轮范围。

完成标准：酒店和景点详情页能读写真实评论；评论问答不会把错误伪装成“没有评论”，且 hotel/attraction 两种目标都能正确区分。

### Phase 5：订单闭环

目标：完成“商品/SKU -> 草稿 -> 创建订单 -> 库存 -> 支付/取消”。

- order-service 保留现有 `PENDING_PAYMENT -> PAID` 和取消流程，补齐会阻断订单闭环的查询、取消和支付接口。
- frontend 增加从房型/SKU 进入订单、查看待支付订单、调用 `ConfirmPayment`、查看 paid/cancelled 状态的入口。
- order-assistant 补齐联系人来源、草稿创建与确认、提交订单、订单查询、取消和 `confirm_payment` 工具。
- 草稿至少在当前进程生命周期内可正确创建、确认和删除；只有跨实例运行成为基础闭环的实际阻碍时，才迁移 Redis。
- 校验 SKU 存在、上架、资源类型、价格、日期和库存；重复 request id 不得创建重复订单。
- inventory-service 保持数据库为库存事实源，确认和释放不能只记录日志后返回成功。

完成标准：用户可以从房型/SKU 创建订单，订单能锁库存；模拟支付后状态为 `PAID`；取消未支付订单后库存释放。

### Phase 6：部署与可观测性基线

目标：单份 Compose 启动后，业务服务和基础设施依赖可用，日志、指标和 trace 能被查询。

- 选定 root `docker-compose.yaml` 作为本地验收 canonical Compose；`deploy/docker-compose/docker-compose.yaml` 必须同步保留服务和基础设施清单，允许使用环境变量表达地址和凭据。
- 保留并补齐 Nacos、Higress、MongoDB、PostgreSQL、Redis、Qdrant、Neo4j、OTel Collector、Tempo、Prometheus、Grafana 的健康检查、依赖顺序、持久化目录和容器内地址。
- 增加 Loki 单实例服务和 Grafana Alloy 日志采集服务，采集保留服务的 stdout/stderr，并按 `service`、`environment`、`level`、`request_id`、`trace_id`、`user_id`、`task_id` 等字段查询；禁止采集 JWT、密码和 API key。
- OTel Collector 必须转发 trace 到 Tempo、指标到 Prometheus，并接收应用日志或与 Alloy 的日志链路保持一致；不能只保留 debug exporter。
- Grafana 预置 Prometheus、Tempo、Loki 数据源，并提供能验证六条闭环的基础 dashboard/查询入口。
- Prometheus 至少抓取 OTel Collector、自身和保留服务暴露的健康/指标端点；没有指标端点的服务必须通过 OTel 或健康检查纳入可观测性。
- Higress 必须有可验证的 OpenAI 兼容 chat/embedding 路由；Nacos 必须能完成服务注册和发现；业务服务启动失败时不能静默绕过必要依赖。
- 不做 Loki/Tempo/Prometheus/Grafana 的集群、复制和自动故障转移，使用本地卷保存数据即可。

完成标准：`docker compose up` 后，六条闭环依赖健康；可以用 Grafana/Loki 查到一次订单、评论或行程请求的日志、指标和 trace；模型请求通过 Higress，Python gRPC 客户端能通过 Nacos 发现 Java 服务。

### Phase 7：删除无用服务与总验收

目标：运行系统只保留六条闭环所需的服务。

- 按“服务目录 -> Taskfile -> Compose -> protobuf/生成入口 -> frontend/env -> 文档和测试客户端”的顺序删除 POI、File、Note、Note Creator 和 RocketMQ 引用。
- 保留共享 POI 类型和初始化数据，删除独立 POI service 的调用入口。
- 运行全仓引用检查，确认删除项不再出现在构建、启动和业务代码中。
- 用 initializer 导入固定用户、景点、酒店、房型、SKU、库存和评论数据。
- 按六条闭环和基础设施顺序执行 smoke test；任何失败都回到对应 Phase 修复，不以“服务能启动”作为完成标准。

## 5. 六条闭环验收

1. 用户 A/B 分别注册登录，确认 JWT/session 可用，现有业务请求能够正常携带所需身份参数。
2. 登录后读取景点、酒店、房型、SKU；确认 planner 和 order-assistant 读取同一实体。
3. 用户生成行程，刷新和编辑保存。
4. A 查看酒店/景点评论并完成创建、更新、删除流程。
5. A 在详情页或主聊天询问评论，回答必须对应正确的酒店/景点；无评论、无索引、服务失败必须区分。
6. A 选择 SKU 创建订单，确认库存锁定，模拟支付到 `PAID`；取消未支付订单后释放库存。
7. 启动和构建检查不得再包含被删除服务；共享 POI 类型仍能通过 protobuf 生成和行程服务编译。
8. 查询 Grafana、Loki、Prometheus 和 Tempo，确认至少一条真实业务请求可以按服务名、request id 和 trace id 关联定位。

## 6. 完成判定

本轮完成的含义是：

- 六条闭环都有真实入口、真实数据和可重复验收路径。
- 单实例 Compose 能启动完整业务依赖；Nacos、Higress 和观测组件不是“启动但未接入”的孤立容器。
- 关键写操作按认证身份校验所有权。
- 订单、库存和评论不会返回与事实相反的成功结果。
- 基础失败能被用户或调用方识别，不把依赖故障伪装成空数据。
- 无调用方服务已从代码、构建和 Compose 入口删除。

以下内容留到后续专项，不阻塞本轮：高可用、服务副本与复制、自动故障转移、跨实例一致性、完整幂等/补偿状态、共享 checkpoint、MCP 协议迁移、F1-F5 故障注入和 MinIO 清理。
